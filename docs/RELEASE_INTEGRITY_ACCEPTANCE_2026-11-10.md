# Release integrity #266: controlled late-old deployment acceptance

**Observed 2026-11-10.** This is a bounded operational regression and recovery record for the public Vercel deployment. It does **not** grant real model training, change the database, authorize 2025/26 holdout access, or add any secrets.

## Original risk and controls

On 2026-11-09 a late **Git-source** build of an older commit `e9f48e9742be4f4c1c35caf61240b0cb2443d454` gained all three production aliases after the newer protected commit `f5cfb13c9c37eb27dcb448c9752cfbec0a665134` had been deployed. The original trigger (queue/webhook/redeploy/replay) **remains unproven**; Vercel audit and build logs only establish ordering and content. [Issue #266](https://github.com/StanleyLl0yd/FootballForecast/issues/266) has the original event chronology.

Preventive project control: `autoAssignCustomDomains=false` on Vercel Hobby project `prj_GtKAkXudUBwfMwzWznYzni7LtEzu`. Git pushes produce **staged production builds**; promotion of stable user-facing domains requires an explicit reviewed action. The generated `git-main` branch alias is **not** frozen by this setting. Source-of-truth for stable-site readiness: protected GitHub `main`, nine exact-main code/security checks, authenticated Vercel deployment metadata (project, target, READY, `fra1`, exact Git SHA), and authenticated Vercel alias-to-deployment mappings.

## Real 2026-11-10 late-old deployment regression

1. **Before:** protected `main=cd0b208730a00f0fadca5955593c6cc21260eb13`, exact-main **9/9 SUCCESS**. Vercel production `dpl_D2ZgCpAZEDgyVBZPt4mTzCgRw6fw` was `READY`, `fra1`, production-target, exact SHA; **all three** aliases initially pointed to this deployment.
2. Reasserted the project setting `autoAssignCustomDomains=false` through authenticated Vercel settings API (idempotent, no additional keys or providers).
3. Intentionally created a **new production-target redeployment** of the *older* already known deployment `dpl_AQK9ecMX6T25SrJJh2UYci3zuxTB`, with `withLatestCommit=false`, `forceNew=1`. This is **not the same trigger as the original Git-source late build**. The new `dpl_F23G1k73GsbAsxWFduYFXVDcbiE2` was built fresh (no cache), independently confirmed in Vercel build events as `Cloning ... (Branch: main, Commit: 5328a20)`, and reached `READY`, `fra1`, target `production`, source `redeploy`, Git SHA `5328a20cdb4afc127436c9b503f7d748a46d305b`.
4. **After the old build was READY**, three independent authenticated `get_alias` reads established:
   - `footballforecast.vercel.app` **still** pointed to current `dpl_D2ZgCpAZEDgyVBZPt4mTzCgRw6fw` (no rollback).
   - `footballforecast-stanleylloyd-4725.vercel.app` **still** pointed to current `dpl_D2ZgCpAZEDgyVBZPt4mTzCgRw6fw` (no rollback).
   - Generated `footballforecast-git-main-stanleylloyd-4725.vercel.app` **moved to the older** `dpl_F23G1k73GsbAsxWFduYFXVDcbiE2`. This is the accepted non-stable-branch-alias limitation, **not** a claim that all three domains were protected.
5. Triggered the existing owner-only `/release-integrity-check` command on issue #266. GitHub created run [#42816741264](https://github.com/StanleyLl0yd/FootballForecast/actions/runs/42816741264) with `event=issue_comment` at exact protected main. Its job was queued while the generated alias was stale, so **do not cite this as proof that a live monitor observed the mismatch**. The existing offline tests fail closed for an old-SHA alias and a changed protected main; genuine earlier successful owner and scheduled runs already prove the monitor can read live health endpoints, but hourly punctuality is **not** guaranteed.
6. **Recovery pitfall:** `request_promote(current_dpl)` returned **409** (`already the current production deployment`) although the generated alias was wrong. Repeating promotion is therefore **not a valid repair** for this split state. The safe recovery was authenticated `assign_alias` of **only the generated branch alias** to independently checked current `dpl_D2ZgCpAZEDgyVBZPt4mTzCgRw6fw`; Vercel reported `oldDeploymentId=dpl_F23G1k73GsbAsxWFduYFXVDcbiE2`. Subsequent independent reads confirmed **3/3** aliases on the current deployment. No production rebuild, no private data access.

## Operational policy and residual risks

- **Safe default:** do not re-enable `autoAssignCustomDomains`; a normal late stale Git build must not automatically take over the two stable domains. This assertion is supported by multiple live staged Git builds plus the above distinct late old redeploy case. It is **not** a universal Vercel platform guarantee against privileged operations.
- **Before any explicit production promotion:** independently read the current protected main twice (before inspection and just before action); require the intended build's exact Git SHA, project ID, READY, `production`, region `fra1`, all required exact-main checks success. Do not trust only an application-provided health SHA. Never deliberately promote an old-SHA build for a regression.
- **After a new build:** inspect all three alias mappings. For a stale **generated `git-main` alone**, when both stable production domains and the Vercel current production deployment are already at the correct SHA, do **not** repeatedly promote the correct deployment (409). Reassign only that generated alias to the independently SHA-verified current deployment; read all aliases again.
- **If either stable domain changes:** this is a production incident, not an expected staging condition. Preserve audit evidence, validate latest protected main/required checks and Vercel READY SHA, then use deliberately reviewed promotion or alias repair/rollback. Confirm complete live state afterward; do not publish new forecasts or run any DB migration as part of this procedure.
- **Read-only drift monitor:** `.github/workflows/production-release-integrity.yml` checks the exact protected main SHA and no-store `/api/health` on **all three allowlisted** aliases, failing closed if any mismatches, SHA is missing, HTTP fails or main changes. Scheduled GitHub executions can be delayed and are detection, **not automatic restoration**. Failed runner state / delayed notifications must be investigated separately.
- **No atomic provider CAS:** the available Vercel promotion/alias APIs do not expose an authenticated conditional `if-current-main-SHA == expected` precondition. A privileged operator/API token can still intentionally or mistakenly promote an old deployment; manual independent exact-SHA preflight and immediate postflight are required. The project setting blocks *automatic assignment to stable domains* in the verified cases, but this residual privileged-action race is **not proven impossible**.
- **No root-cause attribution:** original 2026-11-09 old Git-trigger initiation remains unknown. The controlled 2026-11-10 test was an explicitly requested redeploy, not forensic replay of the unknown trigger.

### Acceptance scope

The original user-visible incident class, **late old deployment automatically replacing the main public domain**, was tested with a fresh old-SHA build and **did not recur** under the disabled-auto-assignment project setting. The two stable domains remained current throughout. A generated branch alias did drift and was separately corrected; the detailed recovery now has reproducible API evidence. Existing read-only monitor and synthetic old-SHA regression remained in place.

This is **bounded operational acceptance**, not absolute prevention of privileged wrong promotion, not a fully atomic GitHub/Vercel transaction and not proof of the cause of the original event. Maintain these residual limitations in deployments documentation after issue closure.
