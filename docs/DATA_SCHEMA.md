# Data schema

M0 migration `database/migrations/0001_foundation.sql` defines the first thin operational subset: authorization grants, sources, competitions, seasons, teams, matches, source records, forecasts and outcomes. The full schema from the specification (players, coaches, venues, events, per-player/team stats, source ID mapping, snapshots, jobs, training runs and model registry) belongs to M1–M4.

External vendor IDs must not be used as internal primary keys. `source_records` stores vendor ID and payload SHA-256 without automatically treating it as a historically available record. `ff_matches.status` distinguishes incomplete, postponed and awarded matches. Forecasts have unique `(match_id, revision)`, DB-level live-publication cutoff (including server clock checks) and append-only triggers. After a forecast exists, fixture identity and kickoff become immutable; after an evaluation exists, status and scores also become immutable. Trigger reads lock the fixture row to serialize publication and evaluation with fixture updates. Corrections and postponements that require changing referenced fixture identity or kickoff must eventually use explicitly versioned fixture revisions; this is not implemented at M0. Backtests must be kept in distinct tables, never inserted into the live forecast journal. Post-match outcomes are written separately. Hash-format checks alone are not cryptographic attestation of actual dataset contents.

Before enabling licensed data ingestion, authorized forecast publication and real evaluation: add first-class snapshot/revision links, production-recovery safeguards subject to the owner's deferred backup decision (#96), match final-result integrity checks, full probability-distribution validation at publication, and provider-ID mapping. A disposable PostgreSQL 17 CI harness uses `database/tests/` to exercise the foundation migration with an explicit stub for Supabase `auth.users`, `auth.uid()` and browser roles. This is a **simulated Supabase environment**, not proof of production Supabase API or identity behavior. Confirm policy grants, role ownership and JWT semantics again in an actual Supabase instance before deployment.

For Supabase: the RLS authorization helper is in non-exposed `ff_private` rather than `public`, with schema usage and function execution for `authenticated` only. Explicit table `GRANT SELECT` for `authenticated` and `REVOKE` of browser writes supplement the restrictive RLS policies. CI asserts SQL privileges and RLS using a simulated Supabase-role PostgreSQL 17 fixture. Separately, live Supabase Free Frankfurt PostgreSQL 17.11 has all nine RLS tables, anonymous SELECT on only the six intended tables, no anonymous writes and a successful real publishable-key PostgREST refusal probe (2026-10-22). These live checks are not a production backup or proof of owner OAuth.

M0 additional maintenance migration `0003_match_fk_indexes.sql` adds non-destructive indexes covering match `season_id`, `home_id` and `away_id` foreign keys, as recommended by the live Supabase performance advisor. Indexes were also applied to the live Free project as tracked migration `match_fk_indexes_m0`. The 2026-10-23 Supabase Performance Advisor still listed three INFO-level unused FK indexes because the match table was empty; retain them until real workloads allow meaningful evaluation. The unused kickoff index is also retained. Migration `0004_match_status_scores.sql` is applied and validated on live PostgreSQL as `20261023081004_match_status_scores_m0`, requiring NULL scores for scheduled, postponed and cancelled fixtures; see `DEPLOYMENT.md`.

## Generated live Supabase type contract

`apps/web/lib/database.types.ts` is generated from the actual Frankfurt Free PostgreSQL project on 2026-10-18, not reverse-engineered from sample data. Read-only Next.js Supabase REST clients instantiate `createClient<Database>`, allowing TypeScript to check public table and relationship names at build time. The file contains structural metadata only, not actual rows or credentials. After each **approved migration**, regenerate against the real connected project, inspect the diff, keep migration ordering and run all existing exact-head tests. Runtime RLS, integrity and source-rights checks remain mandatory; generated TypeScript is not security enforcement.
