# Data schema

M0 migration `database/migrations/0001_foundation.sql` defines the first thin operational subset: authorization grants, sources, competitions, seasons, teams, matches, source records, forecasts and outcomes. The full schema from the specification (players, coaches, venues, events, per-player/team stats, source ID mapping, snapshots, jobs, training runs and model registry) belongs to M1–M4.

External vendor IDs must not be used as internal primary keys. `source_records` stores vendor ID and payload SHA-256 without automatically treating it as a historically available record. `ff_matches.status` distinguishes incomplete, postponed and awarded matches. Forecasts have unique `(match_id, revision)`, DB-level live-publication cutoff (including server clock checks) and append-only triggers. After a forecast exists, fixture identity and kickoff become immutable; after an evaluation exists, status and scores also become immutable. Trigger reads lock the fixture row to serialize publication and evaluation with fixture updates. Corrections and postponements that require changing referenced fixture identity or kickoff must eventually use explicitly versioned fixture revisions; this is not implemented at M0. Backtests must be kept in distinct tables, never inserted into the live forecast journal. Post-match outcomes are written separately. Hash-format checks alone are not cryptographic attestation of actual dataset contents.

Before production: add first-class snapshot/revision links, immutable archive backups, match final-result integrity checks, full probability-distribution validation at publication, and provider-ID mapping. A disposable PostgreSQL 16 CI harness uses `database/tests/` to exercise the foundation migration with an explicit stub for Supabase `auth.users`, `auth.uid()` and browser roles. This is a **simulated Supabase environment**, not proof of production Supabase API or identity behavior. Confirm policy grants, role ownership and JWT semantics again in an actual Supabase instance before deployment.

For Supabase: the RLS authorization helper is in non-exposed `ff_private` rather than `public`, with schema usage and function execution for `authenticated` only. Explicit table `GRANT SELECT` for `authenticated` and `REVOKE` of browser writes supplement the restrictive RLS policies. CI asserts both SQL privileges and RLS using a simulated Supabase-role PostgreSQL 16 fixture; no live Supabase project has been provisioned yet.

M0 additional maintenance migration `0003_match_fk_indexes.sql` adds non-destructive indexes covering match `season_id`, `home_id` and `away_id` foreign keys, as recommended by the live Supabase performance advisor. Index verification runs in ephemeral PostgreSQL CI; applying to the live Free project and re-checking advisors are tracked separately. The unused kickoff index is retained until real fixture workloads exist.
